# 18 - Linux Memory Management: Virtual Memory and Address Spaces

Understanding processes and system calls gives us a good picture of how software interacts with the kernel.

The next question is fundamental:

> **Where does a process actually live while it is running?**

A process contains instructions, variables, stacks, libraries, buffers, and other data.

All of that requires memory.

But modern Linux systems do not simply give a process a random section of physical RAM and tell it:

> "Here is your memory."

Instead, Linux uses **virtual memory**.

Virtual memory creates an abstraction between the addresses a program uses and the actual physical locations where its data resides.

The basic relationship is:

```text
Application
     ↓
Virtual Address
     ↓
Memory Management Unit
     ↓
Page Tables
     ↓
Physical Address
     ↓
Physical RAM
```

This mechanism is one of the most important foundations of modern operating systems.

---

# 1. Why Do We Need Virtual Memory?

Imagine a computer with:

```text
8 GB RAM
```

Suppose we have three processes:

```text
Process A
Process B
Process C
```

A simplistic operating system might try to divide physical memory between them:

```text
Physical RAM

+----------------------+
| Process A            |
+----------------------+
| Process B            |
+----------------------+
| Process C            |
+----------------------+
| Kernel               |
+----------------------+
```

This creates several problems.

What happens if Process A tries to access Process B's memory?

What happens if Process A needs more memory?

What happens when Process B exits?

What happens if a process needs more memory than is currently available in RAM?

What happens if two processes want to use the same library?

What happens if a process accesses an invalid address?

A simple physical-memory model becomes extremely difficult to manage.

Virtual memory solves many of these problems.

---

# 2. The Basic Idea

Linux gives each process its own **virtual address space**.

Conceptually:

```text
Process A

Virtual Address Space
+---------------------+
|                     |
|       Process A     |
|                     |
+---------------------+
```

And:

```text
Process B

Virtual Address Space
+---------------------+
|                     |
|       Process B     |
|                     |
+---------------------+
```

Each process behaves as though it has its own private memory.

This does **not** mean every process actually owns an entire physical RAM.

Instead, Linux and the CPU translate virtual addresses into physical addresses.

---

# 3. Virtual Address vs Physical Address

This distinction is critical.

A **virtual address** is the address generated by a running program.

A **physical address** refers to an actual location in the machine's physical memory system.

For example, a program might access:

```text
0x7fff12345678
```

That is a virtual address.

The physical RAM location might be completely different:

```text
0x12345678
```

The program generally doesn't need to know the physical address.

The CPU's memory management hardware performs the translation.

```text
Virtual Address
      ↓
     MMU
      ↓
Page Tables
      ↓
Physical Address
```

---

# 4. The Memory Management Unit

The hardware responsible for virtual-to-physical address translation is the:

**Memory Management Unit**

or:

**MMU**

The MMU is part of the processor's memory-management machinery.

Conceptually:

```text
CPU
 │
 │ virtual address
 ▼
MMU
 │
 │ consults translation structures
 ▼
Physical address
 │
 ▼
RAM
```

The application generates virtual addresses.

The MMU helps translate them.

Linux creates and manages the data structures that make those translations possible.

---

# 5. The Process Address Space

A process's virtual address space contains several logically different regions.

A simplified Linux process might look like:

```text
High Addresses
+---------------------------+
| Kernel address space      |
+---------------------------+
|                           |
| Stack                     |
| ↓ grows downward          |
|                           |
|                           |
| Memory mappings           |
| Shared libraries          |
|                           |
| ↑ grows upward            |
| Heap                      |
|                           |
| BSS                       |
| Data                      |
| Text                      |
+---------------------------+
Low Addresses
```

The exact layout varies by architecture, kernel configuration, security features such as ASLR, and the process itself.

The important point is that a process does not see memory as one giant undifferentiated block.

Different regions serve different purposes.

---

# 6. Text Segment

The **text segment** contains the executable instructions of a program.

For example:

```c
int main(void)
{
    return 0;
}
```

The compiled machine instructions for the program reside in memory that is mapped as executable.

Conceptually:

```text
+---------------------+
| Text                |
| machine instructions|
+---------------------+
```

The text region is typically mapped read-only and executable.

This provides an important protection mechanism.

A normal program should not be able to arbitrarily modify its own executable instructions.

---

# 7. Data Segment

The **data segment** contains initialized global and static variables.

For example:

```c
int counter = 100;
```

The variable has a known initial value.

Conceptually:

```text
+---------------------+
| Data                |
| counter = 100       |
+---------------------+
```

---

# 8. BSS

The **BSS** contains certain global and static variables that are initialized to zero or have no explicit initializer.

For example:

```c
int counter;
```

Conceptually:

```text
+---------------------+
| BSS                 |
| counter = 0         |
+---------------------+
```

The operating system does not necessarily need to store large regions of zeros in the executable file.

It can establish the appropriate memory mappings and provide zero-filled pages when required.

---

# 9. Heap

The heap is used for dynamically allocated memory.

For example:

```c
int *ptr = malloc(sizeof(int));
```

The program asks for memory dynamically.

Conceptually:

```text
+---------------------+
| Heap                |
|                     |
| malloc()            |
| malloc()            |
| malloc()            |
+---------------------+
```

The heap can grow as the process requests more memory.

The C library's `malloc()` ultimately relies on kernel mechanisms such as `brk()` and `mmap()` to obtain memory from the operating system.

---

# 10. Stack

The stack stores information associated with function execution.

For example:

```c
void function(void)
{
    int x = 10;
}
```

The variable `x` may reside on the stack.

The stack also participates in storing things such as:

* function call information
* local variables
* saved registers
* function arguments
* return information

Conceptually:

```text
+---------------------+
| Stack               |
|                     |
| function()          |
| local variables     |
| call information    |
+---------------------+
```

On common architectures, the stack grows toward lower virtual addresses.

---

# 11. Shared Libraries

Modern programs depend heavily on shared libraries.

For example:

```text
libc
```

A process may use functions such as:

```c
printf()
malloc()
open()
read()
```

without containing all of their implementation directly inside its executable.

Linux maps shared libraries into the process's virtual address space.

Conceptually:

```text
Process
+---------------------------+
| Program                   |
+---------------------------+
| libc.so                   |
+---------------------------+
| Other shared libraries    |
+---------------------------+
```

Multiple processes can potentially map the same physical library pages.

This is one of the major benefits of virtual memory.

---

# 12. Each Process Gets Its Own View

Consider:

```text
Process A
```

and:

```text
Process B
```

Both might access:

```text
0x400000
```

But those virtual addresses don't necessarily refer to the same physical memory.

For example:

```text
Process A

Virtual 0x400000
       ↓
Physical 0x120000
```

while:

```text
Process B

Virtual 0x400000
       ↓
Physical 0x850000
```

The same virtual address can therefore refer to different physical memory depending on the process currently executing.

This is one of the most important concepts in virtual memory.

---

# 13. Address Translation

Let's follow a memory access.

Suppose a process executes:

```c
x = *ptr;
```

The CPU needs to read memory.

The program has a virtual address:

```text
Virtual Address
       ↓
     MMU
       ↓
Page Tables
       ↓
Physical Address
       ↓
Memory
```

The translation happens through the processor's memory-management hardware.

Linux is responsible for constructing and maintaining the page-table structures that the hardware uses.

---

# 14. Memory Is Divided Into Pages

Virtual memory isn't normally managed byte-by-byte.

Instead, memory is divided into fixed-size blocks called:

**Pages**

A common page size on x86-64 Linux is:

```text
4 KiB
```

So instead of individually managing:

```text
byte 1
byte 2
byte 3
...
```

the operating system manages blocks:

```text
Page 0
Page 1
Page 2
Page 3
...
```

Physical memory similarly has corresponding units called:

**Page frames**

So:

```text
Virtual memory
     ↓
   Pages
```

and:

```text
Physical memory
     ↓
Page frames
```

---

# 15. Virtual Pages and Physical Page Frames

Suppose we have:

```text
Virtual Page 100
```

Linux might map it to:

```text
Physical Page Frame 5000
```

Conceptually:

```text
Virtual Address Space

Page 100
   │
   │ mapping
   ▼
Page Frame 5000
```

Another process might map its own virtual page 100 to a completely different physical frame.

```text
Process A:

Virtual Page 100
       ↓
Physical Frame 5000
```

```text
Process B:

Virtual Page 100
       ↓
Physical Frame 8000
```

This is the foundation of process isolation.

---

# 16. Page Tables

How does the CPU know this mapping?

Through **page tables**.

Conceptually:

```text
Virtual Page
     ↓
Page Table
     ↓
Physical Frame
```

A page-table entry contains information about the mapping.

It can describe things such as:

* physical frame location
* whether the page is present
* whether it is writable
* whether it is accessible from user mode
* whether it has been accessed
* whether it has been modified

So the mapping isn't simply:

```text
Virtual → Physical
```

It is closer to:

```text
Virtual Page
     ↓
+------------------------+
| Physical frame         |
| Present                |
| Writable               |
| User accessible        |
| Accessed               |
| Dirty                  |
+------------------------+
```

---

# 17. Why Protection Bits Matter

Suppose a process tries to write to a read-only page.

The CPU can detect the violation.

For example:

```text
Process
   ↓
Write memory
   ↓
Page marked read-only
   ↓
CPU detects violation
   ↓
Page fault
   ↓
Kernel
```

This is one of the places where your previous interrupt and exception lessons connect directly to memory management.

A page fault is a CPU exception.

The CPU transfers control into the kernel.

Linux then determines why the fault occurred.

---

# 18. User Space and Kernel Space

Linux separates memory access into different privilege domains.

Conceptually:

```text
Virtual Address Space
+---------------------------+
| Kernel Space              |
+---------------------------+
|                           |
| User Space                |
|                           |
+---------------------------+
```

A normal user-space process should not be able to freely access kernel memory.

This protects the operating system.

Without this separation, a normal application could potentially overwrite kernel data structures and compromise the entire machine.

---

# 19. User Space

User space contains the normal application environment.

For example:

```text
Your program
Python
Node.js
Chrome
SSH
Shell
```

These applications execute with restricted privileges.

They cannot directly perform arbitrary kernel operations.

They must use controlled interfaces such as system calls.

This connects directly to your previous lesson.

```text
Application
     ↓
System Call
     ↓
Kernel
```

---

# 20. Kernel Space

Kernel space contains privileged operating system code and data.

This includes things such as:

* kernel code
* kernel data structures
* device drivers
* memory-management structures
* networking subsystems
* filesystem code

The kernel needs access to hardware and system resources.

Applications generally do not.

---

# 21. The Connection Between System Calls and Memory

Suppose a process executes:

```c
read(fd, buffer, 4096);
```

The process passes a pointer:

```text
buffer
```

That pointer is a **user-space virtual address**.

The kernel receives the system call.

But the kernel cannot blindly trust the pointer.

The user program could provide:

```text
0xdeadbeef
```

or some address that isn't valid.

The kernel must safely validate and access user memory.

So:

```text
User Process
    ↓
User virtual address
    ↓
System call
    ↓
Kernel
    ↓
Safely access user memory
```

This is why memory management is tightly connected to system calls.

---

# 22. `mmap()`

One of the most important memory-related system calls is:

```c
mmap()
```

It allows a process to create memory mappings.

For example, shared libraries are commonly mapped into virtual memory using mechanisms built around `mmap()`.

Files can also be mapped into memory.

Conceptually:

```text
File
 ↓
mmap()
 ↓
Virtual memory
```

The process can then access the mapped region like memory.

This is extremely powerful.

---

# 23. Memory-Mapped Files

Suppose we have:

```text
data.bin
```

Instead of repeatedly calling:

```text
read()
read()
read()
```

a program can map the file into its virtual address space.

Conceptually:

```text
Disk
 ↓
File
 ↓
mmap()
 ↓
Virtual Memory
 ↓
Process accesses memory
```

The kernel handles the relationship between the virtual memory mapping and the underlying file.

This becomes especially important when we later study filesystems and page cache behavior.

---

# 24. Virtual Memory Does Not Mean Everything Is in RAM

This is an extremely important point.

A process can have a large virtual address space without all of that virtual memory currently occupying physical RAM.

For example:

```text
Virtual memory:

100 GB
```

does not necessarily mean:

```text
100 GB of RAM
```

is currently being consumed.

Some pages may be:

* unmapped
* not yet allocated
* backed by files
* shared
* swapped out
* lazily allocated

This is one reason virtual memory is so powerful.

---

# 25. Lazy Allocation

Linux often delays physical memory allocation until it is actually necessary.

Imagine:

```c
char *buffer = malloc(1GB);
```

The program has requested a large amount of memory.

That doesn't necessarily mean Linux immediately finds and assigns 1 GB of physical RAM to every byte of the allocation.

Instead, Linux can establish virtual memory structures and allocate physical pages as they become necessary.

Conceptually:

```text
malloc()
   ↓
Virtual memory available
   ↓
Program actually accesses page
   ↓
Page needs physical backing
   ↓
Physical page allocated
```

This is called **lazy allocation**.

---

# 26. Demand Paging

A related mechanism is **demand paging**.

The operating system can wait until a page is actually needed before bringing or creating its physical backing.

Conceptually:

```text
Process accesses page
        ↓
Page not currently available
        ↓
Page fault
        ↓
Kernel handles fault
        ↓
Page becomes available
        ↓
Instruction continues
```

A page fault therefore isn't automatically an error.

This is an important misconception to eliminate.

Some page faults are completely normal parts of virtual memory operation.

---

# 27. Page Fault Does Not Always Mean Crash

There are different reasons for a page fault.

A legitimate page fault might occur because:

```text
Page hasn't been allocated yet
```

or:

```text
Page is backed by a file and needs to be loaded
```

or:

```text
Copy-on-write is required
```

An invalid memory access can also cause a fault.

For example:

```text
Process
   ↓
Access invalid address
   ↓
Page fault
   ↓
Kernel determines access is invalid
   ↓
SIGSEGV
```

So the sequence:

```text
Page Fault
```

doesn't automatically mean:

```text
Segmentation fault
```

The kernel determines what the fault means.

---

# 28. Copy-on-Write

Now we can connect memory management to your earlier process lessons.

Suppose Process A calls:

```c
fork();
```

The new process initially needs a copy of the parent's memory state.

A naive implementation could immediately duplicate every physical page.

That would be expensive.

Instead, Linux uses **Copy-on-Write**, commonly called:

**COW**

Conceptually:

```text
Before fork()

Process A
   ↓
Physical Page 1
```

After `fork()`:

```text
Process A ───┐
             ├──> Physical Page 1
Process B ───┘
```

Both processes can initially share the same physical page.

The pages are marked so that a write triggers special handling.

---

# 29. Copy-on-Write in Action

Suppose:

```text
Process A
Process B
```

share a physical page.

Process B writes to it.

```text
Process B
    ↓
Write
    ↓
Page is shared
    ↓
Page fault
    ↓
Kernel creates private copy
    ↓
Process B gets new page
```

Now:

```text
Process A ──> Page 1
Process B ──> Page 2
```

This saves enormous amounts of unnecessary copying.

---

# 30. Address Space Isolation

Virtual memory provides process isolation.

Consider:

```text
Process A
```

and:

```text
Process B
```

Process A cannot simply access Process B's private memory.

Why?

Because the page tables used for Process A don't normally map Process B's private pages into Process A's accessible address space.

Conceptually:

```text
Process A page tables
      ↓
A's memory

Process B page tables
      ↓
B's memory
```

This is one of the fundamental security boundaries of an operating system.

---

# 31. Context Switching and Address Spaces

You previously studied context switching.

Now we can extend the concept.

A context switch doesn't only involve:

```text
CPU registers
```

The processor also needs to operate using the correct address-space translation context for the process being executed.

Conceptually:

```text
Process A
   ↓
Address Space A
   ↓
CPU executes

Context switch

Process B
   ↓
Address Space B
   ↓
CPU executes
```

On x86-64, the active page-table root is associated with the processor's control registers, notably `CR3`.

When the active address-space context changes, the processor's memory translation machinery must reflect the new process.

This is one reason address-space switching has performance implications.

---

# 32. The TLB

Page-table walks can be expensive.

Imagine every memory access required the CPU to repeatedly walk page tables.

That would be slow.

Modern processors therefore maintain a cache of recent virtual-to-physical translations called the:

**Translation Lookaside Buffer**

or:

**TLB**

Conceptually:

```text
Virtual Address
      ↓
     TLB
   ↙     ↘
Hit       Miss
 ↓          ↓
Physical   Page-table
address    walk
            ↓
        Translation
```

A TLB hit means the processor already knows the relevant translation.

A TLB miss means the processor must perform additional translation work.

We will examine the TLB in much greater depth later.

---

# 33. Why Memory Management Is a Performance Problem

Consider a server running thousands of processes.

Every process has virtual memory.

The CPU constantly performs memory accesses.

The system must efficiently manage:

```text
Virtual addresses
Page tables
TLBs
Physical memory
Cache
NUMA
Page faults
Memory allocation
```

Poor memory behavior can produce:

* high latency
* CPU overhead
* cache misses
* TLB misses
* excessive page faults
* memory pressure
* swapping
* NUMA penalties

This is why memory management becomes critical in enterprise infrastructure.

---

# 34. NUMA Connection

You already studied NUMA.

Now we can connect it to memory.

Suppose a server has:

```text
CPU 0
  │
  └── NUMA Node 0
       └── RAM 0

CPU 1
  │
  └── NUMA Node 1
       └── RAM 1
```

Memory physically closest to CPU 0 is generally cheaper for CPU 0 to access than memory attached to another NUMA node.

Virtual memory hides physical location from the application.

But the physical location still matters for performance.

Conceptually:

```text
Virtual Address
      ↓
Page Table
      ↓
Physical Page
      ↓
NUMA Node
      ↓
Physical RAM
```

So virtual memory doesn't eliminate NUMA.

It abstracts the physical memory layout while the kernel still has to manage that topology intelligently.

---

# 35. Virtual Memory and Security

Virtual memory also contributes heavily to security.

Memory permissions can distinguish:

```text
Readable
Writable
Executable
User-accessible
Kernel-only
```

For example, a page might be:

```text
Read + Execute
```

but not:

```text
Write
```

This makes it harder for an attacker to turn arbitrary writable memory into executable code.

Modern Linux systems use multiple hardware and kernel security mechanisms around memory protection.

The important principle is:

> **Memory mappings have permissions.**

---

# 36. ASLR

Linux also uses:

**Address Space Layout Randomization**

or:

**ASLR**

The idea is to randomize important memory locations so that they aren't always predictable.

Without randomization, an attacker might know:

```text
libc = 0x7ffff7000000
stack = 0x7ffffff00000
```

With ASLR, these locations can vary between executions.

You can inspect the general effect experimentally.

Run:

```bash
cat /proc/sys/kernel/randomize_va_space
```

A common value is:

```text
2
```

which indicates a strong form of address-space randomization.

---

# 37. Inspect a Process's Address Space

Linux provides a fantastic interface for examining process memory.

Start a process:

```bash
sleep 1000
```

Find its PID:

```bash
pgrep sleep
```

Suppose the PID is:

```text
1234
```

Now inspect:

```bash
cat /proc/1234/maps
```

You might see something resembling:

```text
55a100000000-55a100001000 r--p ...
55a100001000-55a100002000 r-xp ...
55a100002000-55a100003000 r--p ...
55a100003000-55a100004000 rw-p ...
7f2000000000-7f2000020000 r-xp ... libc.so
7fff00000000-7fff00021000 rw-p ... [stack]
```

Your actual addresses will differ.

This is your first direct look at a real Linux process's virtual address space.

---

# 38. Understanding `/proc/<pid>/maps`

A line from the output might look like:

```text
7f1234000000-7f1234020000 rw-p 00000000 00:00 0
```

The important fields include:

```text
start address
-
end address

permissions

offset

device

inode

pathname
```

For example:

```text
rw-p
```

means approximately:

```text
r = readable
w = writable
x = executable
p = private mapping
```

So:

```text
r-xp
```

means:

```text
readable
executable
private
```

# 43. Lab: Observe Virtual Memory Growth

Create a program that allocates memory:

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(void)
{
    size_t size = 1024UL * 1024UL * 1024UL;

    char *buffer = malloc(size);

    if (!buffer) {
        perror("malloc");
        return 1;
    }

    printf("Allocated virtual memory.\n");
    printf("PID: %d\n", getpid());

    sleep(300);

    free(buffer);

    return 0;
}
```

Compile:

```bash
gcc memory_alloc.c -o memory_alloc
```

Run it.

Then inspect:

```bash
cat /proc/<PID>/status
```

Look at:

```text
VmSize
VmRSS
```

This experiment introduces a crucial distinction.

### VmSize

Roughly represents the process's virtual memory size.

### VmRSS

Roughly represents the resident set, meaning memory currently resident in physical RAM.

They don't necessarily have to be equal.

That difference is one of the most important practical demonstrations of virtual memory.

# 44. A More Interesting Experiment

Modify the program so that it allocates a large region but doesn't immediately touch every page.

Then compare:

```text
VmSize
```

and:

```text
VmRSS
```

before and after touching the memory.

For example:

```c
for (size_t i = 0; i < size; i += 4096)
    buffer[i] = 1;
```

Why increment by:

```text
4096
```

?

Because a common Linux page size is 4 KiB.

You're deliberately touching approximately one byte in each page.

Now observe the change in:

```text
VmRSS
```

This demonstrates lazy allocation and demand paging much more clearly.

# 45. What Just Happened?

Before touching the memory:

```text
Virtual allocation
       ↓
Pages may not all have physical backing
```

After touching each page:

```text
Memory access
       ↓
Page required
       ↓
```

# 52. What You Should Be Able to Explain

Before moving to the next chapter, you should be able to answer these questions.

### 1. What is virtual memory?

An abstraction that gives processes virtual address spaces while allowing the operating system and hardware to manage the underlying physical memory.

### 2. What is a virtual address?

An address generated and used within a process's virtual address space.

### 3. What is a physical address?

An address corresponding to a location in the system's physical memory address space.

### 4. What translates virtual addresses?

The CPU's memory-management hardware, primarily through the MMU and page-table structures.

### 5. What is a page?

A fixed-size unit of virtual memory.

### 6. What is a page frame?

A fixed-size unit of physical memory that can back a virtual page.

### 7. What is a page table?

A data structure containing mappings and permissions used to translate virtual pages to physical frames.

### 8. Why does each process have its own address space?

To provide isolation, protection, and an independent memory abstraction.

### 9. Does allocating virtual memory immediately mean physical RAM is allocated?

Not necessarily. Linux can use lazy allocation and demand paging.

### 10. What happens when a required page isn't currently available?

The CPU can generate a page fault, allowing the kernel to determine how the fault should be handled.

### 11. Why is `fork()` efficient?

Because Linux can initially share pages between parent and child using Copy-on-Write rather than immediately copying every page.

### 12. What is the TLB?

A processor cache of recent virtual-to-physical address translations.

### 13. What is the relationship between virtual memory and NUMA?

Virtual memory abstracts physical location, while the kernel still needs to place and manage physical pages intelligently across NUMA nodes for good performance.
