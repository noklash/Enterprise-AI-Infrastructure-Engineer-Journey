## 2. Why This Session Exists

You already understand what systemd does once it is running: units, targets, dependencies, and the journal.  

The remaining question is **how the system reaches the point where systemd can do that work**, and what happens in the ordered sequence of targets after systemd takes over.

A boot failure can occur in several distinct regimes:

- firmware / hardware initialisation  
- bootloader  
- kernel + initramfs  
- transition from initramfs to the real root  
- systemd early targets (local-fs, sysinit, basic)  
- later targets (multi-user, graphical) and the services they pull in  

Each regime has different symptoms, different logs, and different recovery tools. Treating “the machine won’t boot” as a single problem leads to random guessing. This session builds a staged mental model and the practical commands that belong to each stage.

## 4. Prerequisite Concepts

You already know:

- systemd is PID 1 and activates units according to a dependency graph.  
- Targets are milestones; the default target is what a normal boot aims for.  
- The journal can record the current and previous boots.  
- Mount units and `local-fs.target` are part of making filesystems available.  
- The kernel mounts an initial root and then executes an init process.

## 5. Mental Model

```
Power on
    │
    ▼
Firmware (BIOS / UEFI)
    │  hardware init, boot device selection
    ▼
Bootloader (GRUB, systemd-boot, …)
    │  load kernel + initramfs, pass cmdline
    ▼
Kernel
    │  init hardware drivers, mount initramfs as root
    ▼
Initramfs user space
    │  find real root, unlock crypto, assemble RAID/LVM, …
    │  pivot / switch_root to real root
    ▼
systemd (PID 1 on the real root)
    │
    ├─ local-fs.target / swap.target
    ├─ sysinit.target
    ├─ basic.target
    ├─ multi-user.target   ← typical server default
    └─ graphical.target    ← if desktop
```

Failure modes and tooling differ above and below the “systemd becomes PID 1 on the real root” line.

## 6. Core Concept

### Firmware (BIOS / UEFI)

- Initialises CPU, memory controller, and core devices.  
- Applies firmware policy (Secure Boot, boot order).  
- Locates a bootloader on the selected device (UEFI: EFI System Partition; legacy: MBR/GPT + stage1).  

You rarely debug firmware itself from Linux, but wrong boot order, disabled Secure Boot keys, or missing EFI entries are common “machine won’t start” causes in data centres and laptops.

### Bootloader

On most Linux servers and VMs this is **GRUB 2**. Responsibilities:

- Present a menu (or apply a default).  
- Load the kernel image and the initramfs into memory.  
- Pass the kernel command line (`root=`, `ro`, systemd options, console settings, …).  
- Chain-load another loader if needed.

Configuration lives under `/boot/grub/` or `/boot/efi/…` and is usually generated by `grub-mkconfig` from files in `/etc/default/grub` and `/etc/grub.d/`.

### Kernel + initramfs

- The kernel decompresses, initialises core subsystems, and mounts the **initramfs** as a temporary root.  
- The initramfs contains a minimal user space (often a small systemd or a script-based init) whose job is to:  
  - load modules needed to reach the real root  
  - activate LVM, RAID, multipath, decrypt LUKS volumes  
  - mount the real root filesystem  
  - execute `switch_root` / `pivot_root` and run the real `/sbin/init` (systemd)

If the initramfs cannot find or unlock the root device, the boot stops in the initramfs emergency shell (or simply hangs).

### systemd on the real root

Once systemd is PID 1 on the real root it walks its dependency graph toward the default target. Important early milestones:

| Target | Rough meaning |
|--------|----------------|
| `local-fs.target` | Local filesystems defined in fstab/mount units are mounted |
| `swap.target` | Swap is active |
| `sysinit.target` | Early system initialisation (journal, udev settlement, …) |
| `basic.target` | Standard base system is ready |
| `multi-user.target` | Non-graphical multi-user system (common server default) |
| `graphical.target` | multi-user + display manager |

Services are pulled in by `Wants=` / `Requires=` relationships from these targets and from each other. Ordering constraints (`After=` / `Before=`) determine the parallelisation limits you measured with `systemd-analyze`.

## 7. Break It Into the Smallest Important Pieces

### 7.1 Firmware boot order / EFI variables
- Decide which device and which loader run first.

### 7.2 Bootloader configuration
- Kernel path, initramfs path, kernel command line, default entry, timeout.

### 7.3 Kernel command line
- Arguments such as `root=UUID=…`, `ro`, `quiet`, `systemd.unit=…`, `rescue`, `emergency`.  
- Visible later in `/proc/cmdline`.

### 7.4 Initramfs
- Temporary root that prepares the real root.  
- Built by `dracut` or `mkinitcpio` / `update-initramfs` depending on distribution.

### 7.5 switch_root / pivot_root
- Atomic transition from initramfs root to the real root filesystem.

### 7.6 Default target
- The systemd goal of a normal boot (`systemctl get-default`).

### 7.7 Rescue and emergency modes
- `systemd.unit=rescue.target` — single-user, root filesystem mounted, minimal services.  
- `systemd.unit=emergency.target` — even smaller; often used when the root filesystem itself needs repair.  
- Selectable from the bootloader by editing the kernel command line.

### 7.8 Boot measurement
- `systemd-analyze` and `systemd-analyze blame` / `critical-chain` attribute time to individual units.

## 8. What Linux Is Actually Doing

**End-to-end sequence (condensed)**
```
Firmware
    → loads bootloader from ESP or MBR
Bootloader
    → loads vmlinuz + initrd, jumps to kernel entry point with cmdline
Kernel
    → early setup, device discovery, mounts initramfs, starts /init inside it
Initramfs init
    → udev, modules, storage assembly, cryptsetup, mount real root
    → switch_root / exec real systemd as PID 1
systemd
    → default.target → … → multi-user.target (or graphical.target)
    → parallel activation of units respecting After=/Before=
    → system becomes usable (getty, sshd, application services, …)
```

## 9. Commands and Tools

| Command / Path | Purpose |
|----------------|---------|
| `cat /proc/cmdline` | Kernel command line used for the current boot |
| `systemctl get-default` | Default target |
| `systemctl list-units --type=target` | Active targets |
| `systemd-analyze` | Overall boot time |
| `systemd-analyze blame` | Units sorted by time to start |
| `systemd-analyze critical-chain` | Chain of dependencies that limited boot speed |
| `systemd-analyze plot > boot.svg` | Visual timeline (optional) |
| `journalctl -b` | Full journal for the current boot |
| `journalctl -b -1` | Previous boot (if persistent journal) |
| `ls /boot` / `ls /boot/efi` | Kernel, initramfs, EFI artefacts |
| `grub-editenv list` / `grep GRUB /etc/default/grub` | GRUB configuration surface |
| `lsinitramfs` / `lsinitrd` | Inspect initramfs contents (distribution-specific) |

Recovery-oriented: bootloader menu → edit entry → append `systemd.unit=rescue.target` or `emergency.target`, or `single`.

## 10. Hands-On Lab

**Objective**  
Map the boot path on your system, measure it, and inspect the artefacts of each stage that are still visible from a running OS.

**Setup**  
A systemd-based lab VM (VirtualBox is ideal). Persistence of the journal is helpful but not required.

```bash
mkdir -p ~/boot-lab
cd ~/boot-lab
```

**Steps**

1. Kernel command line and default target:
```bash
cat /proc/cmdline
systemctl get-default
systemctl status
```

2. Boot timing:
```bash
systemd-analyze
systemd-analyze blame | head -20
systemd-analyze critical-chain
```

3. Target graph (high level):
```bash
systemctl list-dependencies multi-user.target | head -40
systemctl list-dependencies sysinit.target | head -30
```

4. Bootloader and kernel artefacts:
```bash
ls -l /boot
ls -l /boot/efi/EFI 2>/dev/null || ls -l /boot/efi 2>/dev/null
# GRUB config surface
grep -E 'GRUB_DEFAULT|GRUB_TIMEOUT|GRUB_CMDLINE' /etc/default/grub
```

5. Journal of the current boot and early messages:
```bash
journalctl -b -o short-monotonic | head -40
journalctl -b -u systemd-journald -u systemd-udevd --no-pager | head -30
```

6. (Optional) Generate a plot for later inspection:
```bash
systemd-analyze plot > boot.svg
# Copy off the VM or open with a browser if available
```

7. Identify the initramfs generator used by the distribution:
```bash
ls /usr/sbin/update-initramfs /usr/bin/dracut /usr/bin/mkinitcpio 2>/dev/null
```

**Verification**  
You must be able to state for your lab system:

- The default target.  
- Approximate overall boot time and the two or three slowest units.  
- The kernel command line.  
- Where the kernel and initramfs images live.  
- Whether the previous boot’s journal is available.

**Cleanup**
```bash
rm -rf ~/boot-lab
```

## 11. Investigation Lab

**Scenario**  
A server fails to complete boot after a storage change. The console shows a message about a dependency failure involving a mount unit, then drops to a maintenance prompt (or hangs before multi-user). SSH is not up.

**Objective**  
Determine which stage failed and the first concrete action to take.

**Available tools**  
Console access, bootloader menu, rescue/emergency targets, `journalctl`, `systemctl list-units --failed`, mount/fstab inspection

**Initial clues**  
- Failure occurs after the kernel and initramfs have handed off (systemd messages are visible).  
- A mount or `local-fs.target` related error appears.  
- The host previously booted cleanly before a new disk / fstab entry was added.

**Investigation questions**  
1. How do you tell that the failure is inside systemd’s target graph rather than in the initramfs?  
2. What is the difference between rescue.target and emergency.target for this class of problem?  
3. Which commands, once you have a root shell, show the failed units and the underlying error?  
4. What is the usual recovery pattern for a bad fstab / mount unit entry?

Work the questions before reading the solution.

**Solution**  
Presence of systemd messages and a maintenance shell managed by systemd indicate that the real root was mounted and PID 1 is systemd. The failure is in the unit graph (often a mount unit with `nofail` missing, a wrong UUID, or a device that never appeared).

From the maintenance shell (or after booting with `systemd.unit=rescue.target`):

```bash
systemctl list-units --failed
journalctl -b -p err
systemctl status <failed-mount-unit>
cat /etc/fstab
```
Typical recovery: correct or comment out the bad fstab line, `systemctl daemon-reload`, mount manually to verify, then continue boot (`systemctl default` or reboot). Adding `nofail` (and possibly `x-systemd.device-timeout=`) for non-critical mounts prevents a single missing disk from blocking the entire boot.

## 12. Production Failure Scenario

**Incident**  
A fleet of cloud VMs is updated. A subset no longer becomes reachable over the network after reboot. The cloud serial console shows that the machines reach `multi-user.target` but `sshd` is not listening. Local (serial) login works.

**Systematic troubleshooting**

1. **Observation**  
   Boot completes to multi-user; interactive login on serial works; network service or sshd is not functional.

2. **Hypothesis set**  
   - `sshd` failed to start.  
   - Networking failed or came up after sshd and sshd does not retry.  
   - A packaging change altered unit dependencies or the default target.  
   - Host key generation or a Mount/Permission problem blocks sshd.

3. **Evidence**  
   ```bash
   systemctl status
   systemctl list-units --failed
   systemctl status ssh
   journalctl -b -u ssh -u NetworkManager -u systemd-networkd
   systemctl show ssh -p After -p Wants -p Requires
   ip addr
   ```

4. **Resolution examples**  
   - Fix the failed unit (permissions on `/etc/ssh`, missing host keys, bad `sshd_config`).  
   - Correct ordering if a custom service races with network.  
   - Ensure the network stack used by the image is the one the unit files expect (NetworkManager vs systemd-networkd vs classic scripts).  

5. **Prevention**  
   - Boot-time integration tests in the image pipeline (serial console expectation + ssh readiness probe).  
   - Avoid unnecessary `After=network-online.target` for services that do not need full IP connectivity at start.  
   - Keep journal persistent on cloud images so previous-boot failures remain visible after a forced reboot.

## 13. Connection to Previous Linux Knowledge

- Filesystems and mounts (Sessions 04–06) are activated via mount units and `local-fs.target` during boot.  
- Service units and restart policy (Session 20) determine how application daemons behave once the graph reaches them.  
- The journal (Session 21) is the primary record of everything from early systemd onward; initramfs and bootloader have their own, more limited, logging channels.  
- Block devices and UUIDs (Session 05) appear on the kernel command line (`root=UUID=…`) and in fstab/mount units; mismatches are a classic boot failure.  
- Security modules (Session 18) and capabilities (Session 17) already apply to early services; a MAC denial can prevent a mount or a service from starting and therefore stall a target.

## 14. Connection to Future Infrastructure

- **Cloud images**: almost every public image boots through this exact chain; cloud-init itself is a set of systemd services pulled in early.  
- **Immutable / image-based systems**: bootloader and initramfs become the primary update surface; understanding them is required for safe OS upgrades.  
- **Containers**: the host boot process is what brings up the container runtime; a node that “won’t join the cluster” is often a host that never reached multi-user cleanly.  
- **Kubernetes**: kubelet, cni, and device plugins are systemd services; node NotReady after reboot is frequently a boot-order or failed-unit problem visible with the tools from this session.  
- **AI infrastructure**: GPU nodes must load drivers, mount shared datasets, and start device plugins before training jobs can run; all of that is expressed as units ordered under the same target graph.
